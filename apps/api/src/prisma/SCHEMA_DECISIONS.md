# Schema Decisions

## Refresh Tokens

Refresh tokens are stored in **PostgreSQL** (`refresh_tokens` table), not Redis.

**Rationale:**

- **Defense in depth:** PostgreSQL typically enforces stricter network and auth controls than Redis, making it harder to reach from an attacker who has not fully escalated privileges
- **Durability:** Redis without AOF/RDB persistence configured would silently log out all users on a crash — unacceptable for session data
- **Audit trail:** easy to query active sessions per user and support cascade revocation via `WHERE userId = ? AND revokedAt IS NULL`
- **Explicit expiry management:** expired tokens are cleaned up by a background job; no silent TTL surprises

**Schema fields:**

- `tokenHash` — SHA-256 of the raw token; the raw value is never persisted
- `revokedAt` — set on logout or detected token reuse (cascade revocation)
- `expiresAt` — indexed for efficient cleanup jobs

**Indexes:** `(userId)` for cascade revocation · `(expiresAt)` for cleanup job

See CLAUDE.MD §Authentication for the full flow specification.

## Magic Link Tokens

The `token_hash` column stores the SHA-256 hash of the raw magic link token. The raw value is
generated by the use case, sent once in the email, and never persisted. Validation compares
incoming raw tokens by hashing and looking up `tokenHash`.

One active token per user — requesting a new magic link invalidates any previous unused token.
